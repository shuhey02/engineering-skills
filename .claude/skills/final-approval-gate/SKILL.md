# 最終承認ゲート

## 大原則

実装の良し悪しを最終的に判断するのはユーザーであって、エージェントではない。どれだけ実装に自信があっても、その判断を代行したり省略したりしない。

このスキルは、成果物が後戻りしにくい状態になる直前(PR作成、push、デプロイ、成果物の引き渡しなど)に必ず立ち止まり、やったことを人間が判断できる形に要約して、明示的に「良いか悪いか」を確認するための手順を定める。

## いつ使うか

次のいずれかの直前に、このゲートを通す。

- PRを作成する直前
- git push・デプロイなど、共有環境や外部に影響する操作の直前
- コードに限らず、レポート・設計・分析結果などの成果物を「完成」としてユーザーに引き渡す直前
- 複数ステップにわたる作業の締めくくりで、タスクを「完了」と伝えようとしているとき

これらの操作そのものは明示的に指示されていても(例:「実装してPRを作って」)、確認を後回しにしない。まずこのゲートで要約と確認を行い、承認が得られてから該当のアクション(push・PR作成など)に進む。「自律的に進めてよい」という一般的な指示があっても、この最終確認だけは省略しない。それがこのスキルの存在理由そのものである。

一方、単発の小さな修正や作業途中の中間報告にまで、毎回このゲートを挟む必要はない。目安は「これを境に後戻りが面倒になるかどうか」。細かいやり取りのたびに使うと儀式的で煩わしいものになり、本来重要な最終確認が埋もれてしまう。

## 何をするか

1. 対応した内容を、意味のあるまとまり(セクション)に分ける。分け方はタスクに応じて柔軟に決めてよい(機能ごと、ファイル/モジュールごと、対応した問題ごとなど)。
2. 各セクションについて「何をしたか」「なぜそうしたか」を、平易な言葉で1〜3行程度にまとめる。詳細なdiffやコードをそのまま貼るのではなく、判断に必要な粒度に絞る。
3. ユーザーが理解していないと思われる専門用語を使う場合は、言い換えて済ませようとせず、短い補足説明を添える(例:「〜(◯◯を防ぐための仕組み)」のように用語の直後に補う)。用語を避けることより、正確さを保ったまま理解できる状態にすることを優先する。
4. 迷った点・トレードオフ・確認を取らずに決めた前提など、ユーザーが良し悪しを判断するうえで知っておくべき情報があれば明記する。目的は作業ログを残すことではなく、判断に必要な材料を渡すことにある。
5. 最後に、良いか悪いかを明示的に問う一文で締める。

## 出力フォーマット

見出しの言葉づかいは調整してよいが、「セクションごとの要約」と「明示的な確認の問い」は必ず含める。

```
## [タスク/PRの名前]

### [セクション1]
- 何をしたか / なぜそうしたか

### [セクション2]
- 何をしたか / なぜそうしたか

(必要な数だけ続ける)

### 判断してほしい点(あれば)
- 迷った点やトレードオフ

---
この内容で進めてよいか、直したい点があるか教えてください。
```

## 回答を待つ

要約と確認の問いを出したら、そこで止まる。明示的な返答を待たずに、PR作成・push・デプロイ・成果物の引き渡し・「完了しました」の宣言に進まない。ユーザーが忙しそうだから、内容に自信があるから、といった理由で確認を省略しない。

- 承認の返答(「良い」「OK」など)があれば、そこで初めて該当のアクションに進む。
- 修正の指示があれば、それを反映したうえで、再度このゲートに沿って要約し直し、もう一度確認を取る。承認が得られるまでこれを繰り返す。

## 書き上げたあとのチェック

- [ ] 内容をセクションごとに分けて要約したか(1つの長い文章のまま提示していないか)
- [ ] コードそのものや専門用語の羅列ではなく、判断できる粒度の平易な言葉で書いたか
- [ ] ユーザーが理解していないと思われる用語に、短い補足説明を添えたか
- [ ] 迷った点・トレードオフがあれば明記したか
- [ ] 明示的に「良いか悪いか」を問う一文で締めたか
- [ ] 回答を待たずに、次のアクション(PR作成・push・デプロイ・完了宣言)に進んでいないか
